# Architecture

How Memoir is put together, and where new code goes. `REQUIREMENTS.md` says what it must do.

## Three processes

| Process | What it is | Image |
|---|---|---|
| **API** | FastAPI, `memoir-cli serve`. Applies the migrations on start (under a lock), then serves `/api/...` | `memoir-api` |
| **Worker** | The same Python package, `memoir-cli worker`. Runs background jobs from the job table | `memoir-worker` |
| **Web** | A Vite plus React single-page app, built to static files and served by nginx under `/memoir/` | `memoir-web` |

PostgreSQL 17 holds every record. Files live in the blob store on a volume (`/data/blobs`). In production, Caddy
sends `/memoir/api/...` to the API (stripping `/memoir`) and the rest of `/memoir/...` to the web image. Locally the
web image's nginx forwards `/memoir/api/...` to the API itself, so `make up` needs no other proxy.

## The API package (`api/app/`)

| Where | What goes there |
|---|---|
| `main.py` | `create_app()`: middleware, error handlers, routers. Nothing else. |
| `cli.py` | The commands the images run: `serve`, `worker`, `migrate`, `openapi`. |
| `core/` | Settings (one typed object from `MEMOIR_*` environment variables), the database session, structured errors, logging with request and job ids. |
| `routers/` | One module per resource. A route validates, calls a service, returns. No queries in routes beyond the trivial. |
| `<domain>/` | One package per area of the requirements (`archive/`, `accounts/`, `jobs/`, `blobs/`, and later `capture/`, `timeline/` and so on): its models, its services, its job handlers. |
| `domain/` | One module per entity (model, schemas, service, router), plus `merge.py`, `purge.py`, `pagination.py` and `common.py`. `DATA_MODEL.md` describes them. |
| `capture/` | Upload sessions, finalizing into a memory, and the ffmpeg normalisation job. See `CAPTURE.md`. |
| `jobs/catalog.py` | Every module that registers job handlers; the worker loads them all at start. |
| `accounts/deps.py` | Who is signed in and what they may do: every router depends on `require_role(...)` or `require_executor`. See `ACCOUNTS.md`. |
| `core/audited.py` | The `Audited` mixin: `created_by`, `updated_by`, `updated_at`, `deleted_at`, filled from the request's user. |
| `models.py` | Imports every model, so Alembic and the tests see the whole schema. Add each new model module here. |
| `migrate.py`, `migrations/` | Migrations (Alembic, inside the package so the image carries them). One per change, hand-reviewed; `tests/test_migrations.py` fails when a model has a column no migration made. |

Every file stays under 800 lines and every function under complexity 15 (murphy360/standards). A file that would
grow past the limit is split in the same pull request.

## Errors

Every error the API returns has one shape: `{"error": {"code": "...", "message": "...", "field": null}}`. Services
and routes raise `ApiError(status, code, message, field)`. Unknown routes, wrong methods and invalid requests get
the same shape from the handlers in `core/errors.py`. The web client turns the body back into an `ApiError` with the
same fields.

## Jobs

Anything slow or external is a job: transcription, analysis, imports, photo submission. Never call a provider inside
a request.

- `jobs/queue.py`: `enqueue` (with an optional idempotency key, so asking twice makes one job), `claim` (`FOR UPDATE
  SKIP LOCKED`: each job goes to exactly one worker), `succeed`, `fail` (retry after a doubling backoff, capped at an
  hour, until `max_attempts`; then `failed`).
- `jobs/registry.py`: `@handler("area.kind")` registers a function `(ctx, payload) -> result`. `ctx.progress(...)`
  records progress and keeps the job alive. Raise `PermanentError` when retrying cannot help.
- `jobs/worker.py`: the loop. A background thread refreshes the running job's heartbeat. A job whose heartbeat is
  older than `MEMOIR_JOB_STALE_SECONDS` (five minutes) is taken to be stuck and is claimed again. Each worker keeps
  a row in `worker_heartbeats`; `/api/health` reports the freshest.

## Blobs

`blobs/store.py` keeps every file by the SHA-256 of its bytes, at `/data/blobs/<first two hex digits>/<sha256>`.
Writes are atomic, the same bytes stored twice keep one file, and every read checks the hash, so a file corrupted on
disk is refused rather than served. Other tables refer to a blob by its hash.

## The web app (`web/`)

| Where | What goes there |
|---|---|
| `src/api/` | `openapi.json` (generated by the API: `make openapi`), the typed client and `ApiError`. `schema.d.ts` is generated from the JSON at build time and not committed. |
| `src/app/` | The router, the query cache, the two postures (`Layouts.tsx`, `usePosture.ts`) and the navigation. See `FRONTEND.md`. |
| `src/components/`, `src/lib/` | The design pieces (Button, Field, DateField, EmptyState, Toast, Confirm) and the hooks (URL and stored state, optimistic changes, error text). |
| `src/auth/`, `src/settings/` | Sign-in, invitations, the route guard (`RequireAuth`, `Can`, `RequireRole`), the profile, and the owner's people page. |
| `src/pages/`, `src/features/` | Screens, and the components of one area of the requirements each. |
| `test/` | Vitest with Testing Library. Tests stub `fetch`; they never need the API. |

The base path (`/memoir/`) is baked in at build time (`VITE_BASE_PATH`). The API is always on the same origin, under
the same path.

## Tests

`make test` runs both suites in their images. The API tests start a throwaway PostgreSQL inside the test image
(`api/tests/pg.py`) and run every migration once; each test leaves the tables empty. Set
`MEMOIR_TEST_DATABASE_URL` to use a database of your own instead.
